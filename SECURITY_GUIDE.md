# Security guide (Version 5.1)

The application is a **local desktop tool**. It assumes the *machine* is trusted
and the *files you feed it* are not.

## Network exposure

| Setting | Default | Meaning |
|---|---|---|
| `server.bindAddress` | `127.0.0.1` | Loopback only — nothing on your network can reach the app |
| `server.port` | `4310` | Local port |
| `server.allowLanAccess` | `false` | LAN exposure is opt-in |
| `server.authToken` | `""` | Required when LAN access is on |
| `server.allowedOrigins` | `[]` | CORS allow-list, used only with LAN access |

**Default URL: `http://127.0.0.1:4310`.** The app never binds `0.0.0.0` unless
you set `allowLanAccess: true` in `config/app-config.json` (or `CATALOG_ALLOW_LAN=1`).

When LAN access is enabled the server prints a warning at startup and:

- every request must carry `X-Auth-Token: <server.authToken>`;
- cross-origin requests are refused unless the origin is in `allowedOrigins`;
- state-changing requests must carry `X-Requested-With: us-vehicle-catalog` (CSRF);
- upload, review, export, admin, backup and restore are all behind that guard.

Security headers are always applied: `Content-Security-Policy` (no inline script,
`frame-ancestors 'none'`, `object-src 'none'`), `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, COOP/CORP `same-origin`,
and a restrictive `Permissions-Policy`.

## Formula-injection protection

Uploaded values beginning with `=`, `+`, `-`, `@`, tab or carriage return can be
executed by spreadsheet applications. Protection is on by default
(`exportSecurity.formulaInjectionProtection`).

| Output | Behaviour |
|---|---|
| CSV (standardized, value mappings) | Risky values are prefixed with `'`, which spreadsheet importers treat as a literal-text marker. The text is preserved. |
| XLSX (standardized, change report, review workbook) | Risky values are written as **explicit text cells** with text formatting (`@`). The visible text is unchanged and no cell is ever written as a formula. |
| Numeric year cells generated by the app | Written as real numbers; never altered. |
| Application-generated source URLs (`exportSecurity.trustedHyperlinkFields`) | Left clickable and untouched. |
| Legitimate negatives (`-12.5`, `-1,234.56`, `1e6`) | Recognised as numbers and never modified. |

Every export reports whether protection fired: a
`Formula Injection Protection Applied` column in CSV/XLSX exports, the same line
on the change-report Summary sheet, the `X-Formula-Injection-Protection-Applied`
response header, and `neutralized_cells` in `project_exports`.

The response header reads `Yes`/`No` for XLSX, where the whole workbook is built
before the response starts. CSV is streamed row by row, so the neutralised count
is not known when headers are sent; the header reads `Enabled` and the exact
per-row detail is carried by the `Formula Injection Protection Applied` column
and by `neutralized_cells` in the export history.

Verified end to end against every output type — standardized CSV, standardized
XLSX, change-report workbook, review-only workbook and value-mapping CSV — by
`scripts/formula_matrix.mjs`; results in
`exports/Formula_Injection_Verification.json`.

## Untrusted workbook limits

Configured in `config/app-config.json` under `workbook` / `upload`:

| Limit | Default | Guards against |
|---|---|---|
| `maxFileBytes` | 512 MB | oversized uploads |
| `allowedExtensions` | `.csv`, `.txt`, `.xlsx` | unexpected file types |
| `allowMacroEnabledWorkbooks` | `false` | `.xlsm`/`.xltm`/`.xlsb`/`.xls` and `vbaProject.bin` |
| `maxZipEntries` | 2,000 | entry-count explosions |
| `maxTotalUncompressedBytes` | 2 GB | ZIP bombs |
| `maxCompressionRatio` | 200:1 | ZIP bombs |
| `maxWorksheets` | 64 | worksheet explosions |
| `maxRows` / `maxColumns` / `maxCells` | 1,000,000 / 1,024 / 50,000,000 | resource exhaustion |
| `maxSharedStringBytes` | 256 MB | shared-string table attacks |
| `maxCellLength` | 32,767 | oversized cells (Excel's own limit) |

Before any parser touches an upload, the app reads the ZIP central directory
itself and rejects unsafe entry names (`../`, absolute paths, drive letters,
backslashes, NUL bytes). File **signatures** are inspected, so a ZIP renamed to
`.csv` or a CSV renamed to `.xlsx` is refused.

Nothing in an uploaded workbook is executed: no VBA, no external workbook links,
no embedded objects, no DDE, no formulas, no scripts. Only cell *values* are read.
External-link declarations are recorded as a warning and never followed.

## Filesystem safety

- An uploaded filename is **never** used as a path. Files are stored under a
  generated storage ID (`<timestamp>-<random>.csv`); the original name is kept
  only as display metadata.
- Names are sanitized for traversal, absolute paths, Windows device names
  (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`), and trailing dots
  or spaces; collisions get a numeric suffix.
- Every read and write is resolved with `resolveInside()`, which throws if the
  target escapes the approved directory. Project export folders are derived from
  the numeric project ID, so one project cannot reach another's workspace.

## Canonical catalog immutability

See `Canonical_Immutability_Security_Audit.md`. In short: 27 SQLite triggers make
the Version 4 catalog read-only for every connection, and the only unlock path
requires a private importer token, refuses to run inside standardization
requests, takes a callback rather than SQL, and always restores the lock.

## Reporting and audit

`security_events` records upload rejections, upload warnings, canonical unlocks
and startup recovery. `project_deletions` records what each cleanup removed
(counts and file metadata, never row contents).
